# Assumptions

These are provisional interpretations of details the assignment does not fully
specify. The PDF remains the source of truth; these choices must not change its
required routes, headers, request fields, response fields, or specified status
codes.

| Topic | Assumption | Reason |
|---|---|---|
| Admission unit | A “class” in the API and UI is one grade-and-shift combination (for example, Class 6 – Morning Shift), with its own seat capacity. | The brief explicitly says each shift is treated as a separate class. |
| Student identity | Treat `X-Student-Id` as a string and preserve leading zeroes. The API example contains a 17-digit value, so 17 digits is a provisional assumption based on that example, not an explicitly stated mandatory length. Do not treat this example alone as authority for rejecting other lengths. The UI asks for this identifier and stores it in that browser’s local storage so the student can return after closing the browser. | The brief provides a 17-digit example and requires a student identity, but does not explicitly define an exact registration-number length. It also requires applications to remain visible after reopening the browser. |
| Authentication and roles | Do not add login, user accounts, or role checks. The entered student ID is the UI’s identity; class creation is available from the UI as the school-admin action. | The brief explicitly says login is not required and requires admin and guardian tasks to be performed through the UI, but specifies no authorization mechanism. |
| Class validation and names | Require a nonblank class name and a positive integer `totalSeats`. Do not require class names to be unique. | A usable class needs a name and a positive capacity; the brief defines no naming or uniqueness rule. |
| Hold request body | `POST /classes/{classId}/holds` has no request body; send the student identity only in the required `X-Student-Id` header. | The API contract specifies the header and response but no request fields or body. |
| Seat counts | Count unexpired `HELD` applications as held seats and `CONFIRMED` applications as confirmed seats. `EXPIRED` and `CANCELLED` applications do not consume seats; available seats equal total minus held minus confirmed. | This follows the stated seat-hold, release, and confirmation behavior and the documented response fields. |
| Duplicate applications | For a student/class pair, an unexpired `HELD` application or a `CONFIRMED` application prevents another active application. `EXPIRED` and `CANCELLED` applications do not. | This gives operational meaning to the one-active-or-confirmed-admission rule without preventing a retry after an application has ended. |
| Expiry timing | Interpret `HOLD_DURATION_SECONDS` as a positive duration in seconds, defaulting to 600. Use UTC for `expiresAt`; expiration releases capacity at the deadline without requiring a request. | The brief provides the variable, default, automatic release requirement, and a UTC (`Z`) response example, but does not state time-zone or invalid-configuration behavior. |
| Expired status | The server is authoritative for expiry and returns `EXPIRED` once the deadline has passed, including when a background expiry task has not yet run. The UI may update its countdown and disable confirmation at the deadline without a page reload. | This satisfies automatic expiry and the no-reload UI behavior without depending on a client or a subsequent API call to release a seat. |
| Confirmation | Only the student identified by `X-Student-Id` may confirm their own unexpired `HELD` application. Repeating confirmation for an already `CONFIRMED` application returns the specified confirmed result without counting another seat. | The brief limits confirmation to the student’s own, unexpired hold and requires repeated confirmation not to increase the count. |
| Cancellation | `DELETE /holds/{holdId}` cancels the caller’s own unexpired `HELD` application and returns the specified `204`. It does not undo a confirmed admission; attempts to cancel an already terminal application are conflicts. | The brief requires a cancel action and lists `CANCELLED`, but does not define cancellation of confirmed, expired, or already-cancelled applications. |
| Hold lookup identity | `GET /holds/{holdId}` uses the hold ID as specified and has no student header. Confirmation and deletion enforce the required student header. | No identity header is specified for the lookup endpoint; adding one would alter its contract. |
| Unspecified error statuses | Use `400` for malformed or invalid input, `404` for unknown class/hold IDs, and `409` for business conflicts such as no available seats or an invalid lifecycle transition. All invalid input produces a 4xx response, never a 500. | The brief explicitly requires 4xx for invalid input and specifies 409 when no seat is available, but leaves other error cases unspecified. |
| Error response body | Return JSON error details for errors, without changing any documented success response. The exact error-body fields are not part of the assignment contract. | The brief requires JSON and user-understandable UI errors but specifies no error response schema. |
| IDs and timestamps | Generate IDs in any stable format; examples such as `c_123` and `h_789` are illustrative. Serialize timestamps as ISO 8601 UTC. | The brief explicitly leaves ID format to the implementer and shows an ISO 8601 UTC timestamp. |
| Refresh interval | Refresh class seat summaries and the current student’s application statuses every 3 seconds while the UI is open. | “Every few seconds” is required, but no exact interval is specified. |
| Environment-variable names | Use a documented .NET connection-string environment variable for PostgreSQL and a Vite `VITE_` variable for the frontend API base URL. Keep the API reachable at `http://localhost:8080`. | The brief requires both URLs/connections to be configurable but does not name those variables. |
| Submission deadline | Preserve the stated deadline, 11 November 2026 at 11:59:59 PM, as printed. The PDF does not identify a time zone. | No time zone can be inferred from the assignment text alone. |
| Technology selections | Use .NET 8, PostgreSQL, EF Core with the Npgsql provider, React 18+ with TypeScript and Vite, and xUnit for backend tests. These are implementation selections, not additional product requirements. | The brief mandates the platforms, permits the ORM and frontend language choices, and does not prescribe a test framework. |
| Optional multi-process bonus | If implemented, the seat-capacity invariant must be enforced by PostgreSQL-backed coordination so two backend processes sharing the database cannot oversell seats. | The optional bonus explicitly requires the invariant to hold across two backend processes. |
